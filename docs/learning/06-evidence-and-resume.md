# 问题记录与简历素材

## 你要产出的工作

在 QA-Agent 真实任务上设计样本，亲自执行并检查工具参数和返回值，识别任务理解、操作范围、执行判断或结果解释的问题，再把可重复的检查固化为脚本。实际发现问题时，写清重现、影响、归因和回归；未发现缺陷也可以提交有证据的覆盖与限制。

## 问题分类

| 类别 | 判定线索 |
|---|---|
| 模型判断 | 选错目标、传错参数、无视限制、凭空宣称完成 |
| 工具执行 | 传入参数正确，但工具返回或执行行为不符合工具契约 |
| 流程编排 | 状态推进、等待或依赖处理与既定流程不符 |
| 业务接口 | 实际请求已到达正确目标，响应或状态违背明确业务契约 |
| 数据或断言 | 复用了已注册号码、预期无依据或断言不足 |
| 环境 | 服务、网络、凭证或依赖不可用，不能直接报成产品缺陷 |

分类可以同时涉及多层，先保留事实，再确定主要原因。自动 classification、历史缺陷标题、一次报错都不能代替归因证据。

## 缺陷记录字段

问题 ID、目标版本、用户输入、预期动作、实际调用与结果、最小复现步骤、证据位置、影响、复现次数、归因可信度、修复建议、实际修复和回归结果。只有建议而未修改时，不能写“已优化”或“已修复”。

## 个人贡献边界

你亲自设计、修改、执行、分析或编写的部分才能作为个人工作；项目已有的执行器、工具、运行队列等是项目背景。本轮我编写的测试方案和示例属于辅助材料，不算你已经独立设计或执行的成果。

如果后续确实完成相应工作，简历可以围绕“设计任务级测试样本，验证目标选择、工具参数、执行范围和完成判断，结合调用轨迹及运行报告定位问题，使用 pytest 固化回归”展开。此处只是表述方向，不是已完成经历。

每条最终简历表述都绑定你的执行记录、问题记录或代码。指标使用实际样本和口径，代码已实现、建议改进、实际修复和回归验证分别写。只有实施了改进并完成可比较的前后测试，才讨论提升。
