# 证据与简历素材

## 证据分层

### A 类：个人亲自完成

学习者实际执行、编写或分析，并保留原始输入、输出和时间。只有这类内容可以直接写成“我完成了”。

### B 类：项目已有实现

通过源码、文档或已有测试确认项目具备的能力。可以写成“项目提供了”或“源码实现了”，不能写成个人从零完成。

### C 类：导师辅助

导师帮助定位代码、设计实验、解释结果或整理结构。可以作为学习过程说明，不能包装成个人独立产出。

### D 类：规划或待验证

尚未执行、只有提示词描述、历史记录或推测。只能写“计划验证”或“待确认”，不能写进已完成成果。

## 缺陷记录最小字段

- 编号、标题、发现日期、环境和版本
- 前置条件、最小复现步骤、实际结果、预期结果
- 原始请求、响应、日志、调用轨迹或 run_id
- 主要归因：接口、测试数据/断言、模型判断、工具执行、流程编排、环境
- 影响、严重性、是否可重复、当前状态
- 证据不足时明确写“待确认”，不要先下产品缺陷结论

## 项目总结结构

项目总结按“背景、个人目标、项目已有能力、我完成的工作、发现的问题、验证方法、结果边界、后续改进”组织。每个结果后面附证据索引，指标写明样本数、时间范围、成功定义和排除项。

## 简历表述规则

优先使用这种结构：`针对什么任务，使用什么方法，亲自完成了什么，得到什么可验证结果，保留什么限制`。例如“围绕车易查注册接口，建立手工基线并对照 QA-Agent 的固定执行报告，分析工具调用轨迹和断言证据”，只有在相应实验真的完成后才能使用。

避免以下表述：`实现了智能规划`、`实现了自动修复`、`大幅提升效率`、`准确率达到某值`，除非代码和实验分别证明能力存在，并且指标口径、样本和原始数据完整。

## 证据索引表

| 素材 | 证据位置 | 状态 | 备注 |
|---|---|---|---|
| 项目架构说明 | 源码文件和行号 | 已读实现 | 不是运行验证 |
| 接口基线 | 个人证据目录 | 待验证 | 需脱敏 |
| 固定执行结果 | run 详情和日志 | 待验证 | 记录 revision |
| Agent 轨迹 | 原始调用记录 | 待验证 | 记录每个 tool 参数 |
| 评估指标 | 统计脚本和输入表 | 待验证 | 写清分母 |
| 缺陷 | 缺陷记录和复现证据 | 待验证 | 区分环境问题 |
