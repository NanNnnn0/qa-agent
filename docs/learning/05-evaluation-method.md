# 评估方法

## 三种判断层次

### 确定性断言

适用于 HTTP 状态码、JSON 字段值、字段是否存在、响应头、耗时阈值、工具参数 schema、任务状态枚举、run 统计和 revision 等。它们可以用代码直接判断，但前提是预期本身有可靠来源。

### 任务级评估

适用于“是否理解用户目标”“是否选对项目和用例”“是否完成必要步骤”“是否依据证据给出结论”“是否说明遗留风险”。这类判断需要明确评分规则，并结合调用轨迹、工具输入输出和最终产物，不能只检查最终文本。

### 人工判断和重复运行

适用于结论是否有足够上下文、失败归因是否合理、回答是否遗漏关键风险、任务是否在不同运行中保持一致。人工评审要记录理由；稳定性要固定输入和环境后重复运行。

## 最小任务级评分卡

每项 0 或 1 分，总分 5 分；评分规则可以在样本积累后调整，但调整必须记录版本。

| 维度 | 1 分条件 |
|---|---|
| 目标理解 | 明确测试项目、接口/用例、范围和成功条件 |
| 工具选择 | 使用与任务匹配的工具和 action |
| 参数正确 | project_id、case_id、计划、等待方式等关键参数正确 |
| 执行判断 | 根据预检、run、checks 和响应判断是否完成 |
| 结论质量 | 说明证据、失败归因和遗留风险，没有把环境问题报成产品缺陷 |

总分不是业务通过率，也不是模型能力的普遍结论。它只适用于固定任务集、固定项目和记录的运行条件。

## 评估证据链

每次 Agent 运行至少保留：原始任务、模型请求上下文或 prompt、tool name、工具参数、工具结果、run_id、逐例 checks、最终回复和任务状态。若缺少中间轨迹，只能评价最终文本，不能可靠评价工具选择和任务完成过程。

## 指标口径

- 任务成功率：成功任务数除以实际完成的任务总数，必须说明成功标准、是否排除环境阻塞和样本范围。
- 端到端耗时：从任务提交到最终结论；工具耗时和接口响应耗时分别记录，避免混为一谈。
- 工具调用正确率：关键工具调用参数完全符合预期的任务数除以需要调用工具的任务数。
- 证据充分率：最终结论中能被 run、checks、日志或接口响应直接支持的结论数除以需证明的结论数。
- 恢复率：发生可恢复错误后最终完成的任务数除以出现可恢复错误的任务数，必须先定义什么叫可恢复。
- 成本：若 provider 提供 token 或费用数据，记录输入、输出、总量和计费口径；没有数据时不要估算金额。

## 失败分类顺序

先确认环境和目标地址，再确认工具是否真的执行，再确认 HTTP 请求和响应，再确认断言和测试数据，最后分析模型解释与编排。一个 `HTTP 200`、工具返回 `ok` 或模型说“测试通过”都不足以单独证明任务成功。

## 车易查案例的评估注意事项

注册接口会改变服务端数据，重复运行会受到手机号、用户名和唯一性规则影响。评估前应固定隔离环境或使用一次性数据策略，并把“数据已存在”与接口拒绝逻辑区分开。token、密码和手机号在轨迹、日志和报告中必须脱敏。
