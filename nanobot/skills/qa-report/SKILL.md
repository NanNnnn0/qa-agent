# 测试报告

报告只写三件有证据的事：**跑了什么、结果如何、风险在哪**。不要复述用例全文。

## 数据来源

- `qa_run action=get run_id=...`：summary + 每条 test 的 checks。
- `qa_task action=get task_id=...`：子任务结论与产物。
- `qa_overview`：项目维度的用例/脚本/运行计数。

## 结论分类（每条失败必须归一类）

| 分类 | 判据 | 处置 |
|---|---|---|
| 产品缺陷 | 服务端返回与需求不符、状态码/业务码错误、数据不一致 | 提缺陷，附最小复现 |
| 用例问题 | 断言写错、前置数据不满足、期望值过时 | 修用例后重跑，不算产品失败 |
| 环境问题 | 连接失败/超时/依赖服务未启动（全量 error） | 标记 `blocked_by_env`，不计入失败率 |
| 待确认 | 需求本身模糊 | 列问题清单，不要猜 |

## 缺陷摘要模板

```
【严重级别】P0/P1/P2/P3
【接口/页面】POST /api/orders
【场景】库存不足时下单
【期望】400 + code=1001
【实际】201 + 订单已创建
【复现】
curl -X POST {base_url}/api/orders -H 'Content-Type: application/json' \
  -d '{"sku":"A-1","qty":999}'
【证据】run_xxx / case SHOP-API-002
【初步判断】库存校验缺失，与需求 §3.2 不符
```

## 报告结构

1. **结论**：通过 / 有条件通过 / 不通过（一句话）。
2. **范围**：项目、用例数（api/ui/manual）、脚本数、运行 id。
3. **结果**：passed / failed / blocked_by_env 数量，失败按分类归组。
4. **缺陷清单**：按严重级别排序，每条含最小复现。
5. **覆盖与风险**：未覆盖的验收标准、未执行的自动化、环境限制。
6. **建议**：下一步该补什么（最多 3 条）。

## 口径纪律

- 覆盖率只说"用例覆盖了哪些验收标准"，不要用"测试点数量/接口数量"冒充覆盖率。
- 未执行的用例、跳过的脚本必须显式列出，不能计入通过。
- 同一个失败在多个用例重复出现时合并成一条缺陷，并列出影响的用例编号。
- 环境问题不要写成产品缺陷；不确定就写"待确认"并给出验证方法。
